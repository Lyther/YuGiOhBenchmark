# Concept Zero Research Ledger

Last checked: 2026-09-30

Scope: feasibility and concept selection for [concept-zero.md](concept-zero.md). This is source research and a bounded live lobby check, not duel qualification.

## Inventory, Framing, and Research Coverage

The existing context is [alignment.md](../alignment.md), [README.md](../../README.md), the Node package/lockfile, the lobby client and protocol tests, and twelve pinned upstream checkouts. No earlier concept HLD, architecture, or roadmap was present at inventory. The root source revision was `eb9a77b39920baef826e1fdaaa69345242ff282f`; the live checks below used the working tree, whose test command was `node --test test`. The game-client implementation inspected was the lobby-only source at that revision. Concurrently added [status](../status.md) and [checkout notes](../checkouts.md) were read at closeout; `data/cards/` contained a keep file, not a supplied matching catalogue.

The framing is coherent: evaluate tool-assisted reasoning through real Yu-Gi-Oh play while reusing an existing server. The important tension is between reproducible experiments and a remotely operated, not-yet-identified game/data bundle. The working interpretation is to qualify the chosen endpoint first, preserve exploratory evidence when provenance is incomplete, and make controlled server operation an explicit future decision.

| Research question | Primary evidence examined | Decision consequence |
|---|---|---|
| What is implemented and what has actually run? | Local source/tests, submodule pins, real lobby exchanges | Keep join, playable duel, model acceptance, and benchmark validity as separate claims. |
| What existing components remove custom development? | Server masking/shuffle, WindBot extension, protocol/replay codecs, MCP, card tools | Reuse game/protocol machinery; own only the missing seat and experiment semantics. |
| What does gameplay establish about reasoning? | Game-evaluation papers and existing Yu-Gi-Oh benchmarks | Control decks, tools, context, starting roles, and denominators; do not claim contamination immunity. |
| Can the selected route operate beyond a demo? | Live room settings, relay/source behavior, upstream deployment material, versions/licenses, npm audit | Plausible route exists; long waits, card provenance, client qualification, and distribution remain bounded spikes. |

Research stopped once each critical capability had a credible existing route and the remaining gaps required real integration or operator evidence. Additional benchmark catalogues would not resolve those gaps.

Identify intended distribution, preserve each applicable notice/source obligation, and resolve data rights before publishing assets; these questions do not block local concept research.

## Findings That Change or Qualify the Discussion

| Earlier proposition | Current treatment |
|---|---|
| A public room may force a 240-second game clock. | The default does; the source-derived `TM0,NF#…` room successfully advertised zero time and no banlist in the live handshake. Heartbeats are a different limit. |
| A server path guarantees every privacy property automatically. | It removes raw-core exposure at the transport boundary. Deployed code, cross-seat routing, state labels, handles, logs, and error paths still need verification. |
| WindBot changes are definitely small. | There is a real extension point, but synchronous I/O, incomplete observation forwarding, and platform compatibility make effort unmeasured. |
| Avoiding EDO avoids copyleft issues. | srvpro is also AGPL; the client, core, wrappers, parent repository, and embedded relay have distinct licenses. Evaluate components directly. |
| Hundreds of decisions per duel is an established planning budget. | The 445-decision figure is one YGO-Bench author-reported showcase. Neither a typical horizon nor this project's token cost was measured. |
| All historical defects in alternative bases have been independently reproduced in this research. | Only specifically cited source observations were rechecked. Runtime leak frequency, file access, engine exposure, all seed behavior, and uninitialized nested adapters were not retested. |
| Open deck building and unrestricted card access must be the first benchmark. | The card pool remains unrestricted by banlist; fixed deck assignments are the proposed first experimental sample. Building decks introduces another skill and should receive a separate result. |
